We operate an ecommerce platform. When a customer places an order, the warehouse team
needs to know which shipping box should be used. Each product has dimensions and
weight. Each box has internal dimensions, maximum weight capacity, and cost.
Your task is to design and build a small Django-based system that recommends the most
suitable box for an order.


# Django Shipping Box Recommendation System

For this project, I’d build a small Django application that takes an ecommerce order, checks the dimensions and weights of its products, and recommends the lowest-cost suitable shipping box that can safely accommodate the entire order.

The important part is that the system must handle multiple products in one order, not just select a box for an individual product.

## 1. How the system will work

1\. Customer places an order

Order items, quantities, product dimensions and weights

2\. Calculate package requirements

Combined weight and a feasible arrangement of all products

3\. Evaluate available boxes

Internal dimensions, weight capacity and box cost

4\. Recommend the best box

Select the cheapest box that satisfies all constraints, or explain why no box fits.

## 2. Recommended technology stack

- Backend: Python and Django
- API: Django REST Framework (optional, but useful for a warehouse dashboard)
- Database: SQLite for the initial version; PostgreSQL for production
- Testing: Django's built-in test framework
- Interface: Django templates for a simple warehouse page, or React if a separate frontend is needed

For a small assignment, Django with SQLite and server-rendered templates is sufficient. You can add REST APIs if the ecommerce platform needs to call the recommendation engine.

## 3. Database design

We need four main models: `Product`, `ShippingBox`, `Order`, and `OrderItem`.

| Model       | Important fields                                       |
| ----------- | ------------------------------------------------------ |
| Product     | Name, length, width, height, unit weight               |
| ShippingBox | Name, internal length, width, height, max weight, cost |
| Order       | Order number, creation date, status                    |
| OrderItem   | Order, product, quantity                               |

Use one consistent unit throughout the system: centimeters for dimensions, kilograms for weight, and rupees for cost.

The `OrderItem` model connects products to orders and stores quantities. For example, an order with three units of one product and two units of another contains two order-item records.

## 6. Design the recommendation algorithm

The algorithm should follow these rules:

1. Calculate the total weight of every product in the order, including quantities.
2. Reject boxes whose maximum weight capacity is too low.
3. Check whether every product can fit inside the box in at least one permitted orientation.
4. Check whether all products can fit together without overlapping or exceeding the box's internal dimensions.
5. Among the feasible boxes, choose the one with the lowest cost.
6. If two boxes have the same cost, prefer the smaller box by internal volume.

An important engineering detail: checking each product individually, or checking only the combined product volume, does not guarantee that the complete order fits. For a reliable recommendation, the system needs a three-dimensional packing check.

For an initial version, assume products are rectangular, can be rotated in 90-degree increments, and can be placed next to or on top of each other. Fragile-item constraints, protective packaging and non-stackable items can be added later.

## 7. Implement the box recommendation service

Create `packaging/services.py`. This service contains the core business logic, separate from Django views so it can be reused by an API, warehouse dashboard, or automated order-processing workflow.

The following is a practical greedy 3D packing heuristic. It tries different orientations and placement positions, prioritizing larger products first. It is suitable as a starting point, but it is not a mathematical guarantee that every possible valid arrangement will be found.

```
from itertools import permutationsdef orientations(dimensions):    """Return unique 90-degree rotations of a rectangular item."""    return set(permutations(tuple(float(x) for x in dimensions)))def overlaps(a, b):    """Check whether two placed cuboids overlap."""    ax, ay, az, al, aw, ah = a    bx, by, bz, bl, bw, bh = b    return (        ax < bx + bl and ax + al > bx        and ay < by + bw and ay + aw > by        and az < bz + bh and az + ah > bz    )def can_pack(items, box_dimensions):    """    items: list of (length, width, height) tuples.    box_dimensions: (length, width, height).    Greedy placement; False means this heuristic could    not find an arrangement, not necessarily that none exists.    """    L, W, H = map(float, box_dimensions)    # Try the largest products first.    items = sorted(        items,        key=lambda d: d[0] * d[1] * d[2],        reverse=True,
```

This implementation assumes that product dimensions are accurate and that items can be packed without extra clearance. In production, account for packaging material, dimensional tolerances and any handling restrictions. For orders where packing correctness is critical, replace the greedy heuristic with a stronger 3D bin-packing solver or an exact search for small orders.

## 10. Testing checklist

Before considering the system complete, test these scenarios:

- A single product that fits exactly within a box.
- A product that fits only when rotated.
- Multiple products that fit individually but cannot fit together.
- An order whose total weight exceeds every box's capacity.
- An order with zero items.
- An inactive box that would otherwise be the cheapest.
- Multiple feasible boxes with different costs.
- An order with a product quantity greater than one.

For production use, I would also add an order status such as `pending`, `recommended`, and `packed`, plus a record of the selected box and its cost. That makes recommendations auditable and prevents the warehouse from losing track of which packaging choice was made.

My recommendation: build this as a Django app with a reusable packing service, a REST endpoint, Django admin for managing products and boxes, and automated tests. The key part to validate carefully is the 3D packing algorithm, because an incorrect fit recommendation can lead to real shipping and fulfillment problems.

```
                    Accept: "application/json",
                },
            }
        );

        const data = await response.json();

        if (!response.ok) {
            throw new Error(
                data.error || data.message ||
                "Unable to recommend a box for this order."
            );
        }

        displayResult(data);
        showFeedback("Recommendation calculated successfully.");
    } catch (error) {
        showFeedback(error.message, true);
    } finally {
        button.disabled = false;
        button.textContent = "Recommend box →";
    }
});

```

````
## How It Works

1. Create products with their length, width, height, and unit weight.
2. Define shipping boxes with internal dimensions, maximum weight capacity, cost, and active status.
3. Create an order and add its products with their respective quantities.
4. Enter the order ID in the warehouse dashboard.
5. The backend calculates the total product weight.
6. Boxes that cannot support the total weight are excluded.
7. The packing heuristic evaluates possible product orientations and placements.
8. The system returns the lowest-cost box found that passes the packing check.
9. If no box is found, the API returns an explanatory error response.

## Packing Logic

The recommendation service:

- Calculates total product weight, including quantities.
- Filters out inactive boxes and boxes with insufficient weight capacity.
- Considers 90-degree rotations of rectangular products.
- Attempts to position products without overlapping.
- Evaluates boxes in ascending order of cost.
- Returns the first box for which the heuristic finds a valid arrangement.

**Important limitation:** This implementation uses a greedy 3D packing heuristic. It does not guarantee finding every possible valid arrangement. A failed packing attempt does not prove that a box is physically unsuitable. For production use, consider a stronger packing solver and account for protective packaging, dimensional tolerances, fragile products, and handling restrictions.
````
